Lately I've been thinking about a question. AI can now handle most everyday coding work. But what about software that is technically deep, complex and enormous to build, like a compiler? Can AI do that yet?

The question took me back to a module I built almost three years ago, inside the JIT compiler of an AI framework. Looking at it again is a useful way to see what that kind of work actually involves.

## The project: PIJit in MindSpore

From November 2023 to March 2024 I contributed to **PIJit**, the Python-bytecode JIT compiler in Huawei's open-source deep learning framework [MindSpore](https://github.com/mindspore-ai/mindspore). It takes the same approach as PyTorch's TorchDynamo: it hooks into CPython's frame evaluation (PEP 523), symbolically executes a function's bytecode, and captures as much of it as possible into a static graph that MindSpore can compile and optimise.

When PIJit meets bytecode it cannot put into a graph, it **breaks the graph**. The part before the break is compiled; the rest falls back to the Python interpreter. Fewer breaks means more of the program runs as an optimised graph, so most of my work was about removing breaks without changing what the program does.

In total I opened 13 pull requests, all merged upstream and included in MindSpore v2.3.0.

## The problem: side effects

A compiled graph is a pure function: tensors in, tensors out, nothing else changes. Real Python code is not like that:

```python
@jit(mode="PIJit")
def func(x):                 # x is a list owned by the caller
    x[0] = Tensor([1, 2])    # mutation visible to the caller
    x[1] = Tensor([1, 2])
    return x
```

The graph builder could only rewrite stores into containers created inside the function. For a list passed in by the caller, it gave up, and the function broke at the first assignment.

## The design: record, replace, replay

The side-effect module I wrote keeps the graph pure and moves the mutation outside it:

1. **Record.** When the function writes into an external list, the builder expands the list, builds a *new* list node with the write applied, and records the change.
2. **Replace.** A new-to-old replacement map redirects every reference to the old list (locals, stack slots, closure cells, and parent frames for inlined calls) to the new node, while remembering which real object must be updated later.
3. **Replay.** After the compiled graph returns, generated bytecode replays the writes on the caller's real objects, so the caller sees exactly what eager Python would have done.

With this, functions like the one above compile as a single graph, with the same observable behaviour.

## The hard part was not the code

The core idea fits in three bullet points. Most of the effort went into keeping it correct when it met the rest of the compiler:

- **Replay has to agree with the break point.** If the function breaks later for some other reason, the interpreter runs the remaining bytecode, including its side effects. Any recorded side effect at or after the break must be dropped, or it runs twice.
- **Inlined calls.** A mutation inside an inlined `Cell.construct` has its own records, which must be merged into the top-level graph so replay happens exactly once.
- **Python versions.** The same source compiles to different bytecode on different CPython versions. Python 3.9 turns `[1, 2, 3]` into `LIST_EXTEND` on a constant tuple, which the merge logic did not expect, and a Python 3.7 case needed its own fix.
- **Living with the existing design.** My first version worked but spread its state across several classes. The second version, a few weeks later, pulled recording, clean-up, merging and replay into one `SideEffect` class and absorbed teammates' handling of global writes and `dict.pop`.

None of these rules were written down in one place. They came from reading the graph builder, the bytecode generator and the inliner, and from asking what would break if something ran twice, or not at all.

## What I would improve today

Looking back, the work has gaps I'd fix now: one return value that is silently ignored, an iterator-invalidation bug in the clean-up code, and tests that check the graph-break count but never compare results with eager execution. That last one matters most. A test that only checks "no graph break" can pass while the program computes the wrong answer.

## So, can AI build this?

My current view, from this one module rather than a general theory:

- **Writing each piece is the part AI already does well.** Given a clear spec, generating the replacement map, the bytecode emitter or the test cases is the kind of task today's coding tools handle.
- **Deciding what "correct" means is the hard part.** The real spec was a set of unwritten invariants spread across a large codebase. Getting them right meant understanding the whole system, not one function.
- **Tests decide what gets checked.** My own tests checked the wrong property. An AI working from tests alone would have inherited the same blind spot, and a human can miss it too.

I'm curious how far that boundary moves over the next few years. If you have built something similar, with or without AI help, I'd like to hear how it went.
